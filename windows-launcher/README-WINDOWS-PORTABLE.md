# Direct-Xfer 1.66.6 — Windows portable

`Direct-Xfer.exe` is the .NET 10 (`net10.0-windows`) native Win32 tray/launcher UI. `Direct-Xfer.ServerHost.exe` is the .NET 10 Windows host that supervises the pinned Node.js runtime and the Direct-Xfer backend. Both executables are published **framework-dependent single-file for win-x64** and use the same private shared .NET runtime under `runtime/dotnet`.

The default portable package generated by GitHub Actions contains:
- `Direct-Xfer.exe`
- `Direct-Xfer.ServerHost.exe`
- `runtime/app` — Direct-Xfer 1.66.6 application runtime
- `runtime/dotnet` — one private shared .NET 10 runtime tree used by both Windows EXEs (base Microsoft.NETCore.App runtime only)

**Node.js, rclone and Tesseract are deliberately not included in the default Windows package.** **rclone and Tesseract are deliberately not included in the default Windows package or installer.** The Windows installer first reuses an existing verified Direct-Xfer Node.js runtime or a compatible x64 system Node.js installation. Only when neither is available does Setup download Direct-Xfer's pinned Node.js 24.19.0 `node.exe`, verify its SHA-256, and install it under `runtime/node`. rclone and Tesseract remain downloaded only after explicit activation from the system-tray menu.

Direct-Xfer bundles **one private .NET 10 runtime tree x64** under `runtime\dotnet`. GitHub Actions builds that tree from Microsoft's matching `dotnet-runtime` archive (host + `Microsoft.NETCore.App`) only. The launcher uses native Win32 APIs and does not require `Microsoft.WindowsDesktop.App`. Both `Direct-Xfer.exe` and `Direct-Xfer.ServerHost.exe` resolve this app-relative runtime through `AppHostDotNetSearch=AppRelative`, so the runtime is stored once instead of being duplicated inside both EXEs. **No separate Microsoft .NET Runtime or Desktop Runtime installation is required on Windows.** `Microsoft.WindowsDesktop.App` is not bundled.

The application is intentionally unsigned. Runtime state is stored under `%LOCALAPPDATA%\Direct-Xfer` and the folders selected during first-run setup.

## Optional components

Right-click the Direct-Xfer icon in the Windows system tray and open **Optional components / Composants optionnels**. Each component is downloaded only after an explicit confirmation:

- **rclone 1.74.4** → `%LOCALAPPDATA%\Direct-Xfer\tools\rclone\1.74.4\rclone.exe`
- **Tesseract OCR 5.5.3** → `%LOCALAPPDATA%\Direct-Xfer\tools\tesseract\5.5.3\`

Activating or removing a component signals ServerHost to reload automatically; the main Direct-Xfer installer does not need to be run again. The menu also provides a remove/deactivate action that deletes the per-user optional component.

The rclone archive and Tesseract setup executable are pinned to Direct-Xfer's expected versions and SHA-256 hashes before installation. The `eng`, `fra` and `spa` OCR models are fetched from a pinned immutable `tessdata_fast` commit and validated before activation.

## Storage connectors on Windows

rclone is optional on Windows. Activate it from **system tray → Optional components → Activate rclone** before using Direct-Xfer's rclone-backed storage connectors when no compatible `rclone` is already supplied through `RCLONE_BIN`/`PATH`.

Direct-Xfer keeps its rclone configuration under `%LOCALAPPDATA%\Direct-Xfer\data\rclone\rclone.conf`. Explicit `RCLONE_BIN` and `RCLONE_CONFIG` environment overrides always take precedence over the optional component.

After activation, the per-user rclone configuration can also be edited manually from PowerShell:

```powershell
& "$env:LOCALAPPDATA\Direct-Xfer\tools\rclone\1.74.4\rclone.exe" config --config "$env:LOCALAPPDATA\Direct-Xfer\data\rclone\rclone.conf"
```

## OCR / Tesseract

Tesseract is optional on Windows. In the normal Windows-hosted configuration, server-side OCR remains disabled while the optional Tesseract component is absent. Activate it from **system tray → Optional components → Activate Tesseract OCR**; Direct-Xfer then downloads Tesseract 5.5.3 plus the `eng`, `fra` and `spa` models into the current user's Direct-Xfer tools directory and reloads ServerHost.

Explicit `SEARCH_OCR_ENABLED`, `SEARCH_OCR_TESSERACT_BIN` and `TESSDATA_PREFIX` administrator overrides are preserved. A manually supplied/system Tesseract can therefore still be used without downloading the Direct-Xfer optional component. If the optional component cannot satisfy the requested `SEARCH_OCR_LANGS`, ServerHost does not silently run the incomplete private engine.

Scanned-PDF OCR additionally requires Poppler (`pdftoppm`); searchable PDFs can still use their embedded text layer without Poppler.

## Node.js installation model

The GitHub Actions payload deliberately contains no `runtime/node` directory. During Windows Setup, Direct-Xfer checks, in order, for an already valid private `runtime/node/node.exe`, the previously recorded compatible external Node.js, and a supported x64 Node.js from the system. For 1.66.6, automatic system-runtime reuse is limited to maintained release lines at or above Node 22.23.2, 24.19.0, or 26.7.0; older/EOL/odd-major Node installations are treated as unavailable so Setup falls back to the pinned Node 24 LTS download. If one is usable, no Node.js download occurs. Otherwise Setup downloads the pinned Node.js 24.19.0 x64 executable over HTTPS, verifies SHA-256 `3602f2bb1a10f2cbab4c36886218a33c1ab3db87290e73b033c46c77147d0237`, then copies it into `runtime/node` before ServerHost is started. When an external Node.js installation is reused, Setup stores its exact path, version and SHA-256 receipt under `runtime/node/external-node.ini`; ServerHost rechecks that receipt on every launch so a later binary replacement is not silently trusted.

For a raw portable package that is not installed through Inno Setup, provide a compatible Node.js with `DX_WINDOWS_NODE` and its current SHA-256 in `DX_WINDOWS_NODE_SHA256`.

## Windows payload size optimization

The Windows build creates a dedicated production-only `node_modules` tree with `npm ci --omit=dev` and removes only development metadata (tests, examples, documentation, source maps and TypeScript declarations) while retaining licenses and runtime assets. GitHub Actions enforces the `node_modules` size budget and fails if `runtime\node`, `runtime\rclone` or `runtime\tesseract` accidentally reappears in the default package. Node.js is therefore outside the installer payload itself and is fetched only when Setup actually needs it.
